# ข้อตกลงการทำงานร่วมกันในทีม (Ways of Working - WoW)

เอกสารฉบับนี้จัดทำขึ้นเพื่อกำหนดแนวทางปฏิบัติ กระบวนการทำงาน และมาตรฐานทางวิศวกรรมซอฟต์แวร์ของทีมเรา สำหรับโปรเจกต์ **The Quantified Self Dashboard** เพื่อให้ทุกคนทำงานร่วมกันได้อย่างราบรื่น มีประสิทธิภาพ และรักษามาตรฐานของโค้ดให้อยู่ในระดับสูง

## 1. รอบการประชุม (Meeting Cadence)
เพื่อให้การพัฒนาซอฟต์แวร์เป็นไปอย่างรวดเร็วและส่งมอบงานได้ตรงจุด เราจะนำกรอบการทำงานแบบ Agile อย่างง่ายมาปรับใช้ดังนี้:

| กิจกรรม (Meeting) | ความถี่ | ระยะเวลาที่แนะนำ | เป้าหมาย / สิ่งที่ต้องทำ |
| :--- | :--- | :--- | :--- |
| **Sprint Planning**<br>(วางแผนประจำสัปดาห์) | สัปดาห์ละ 1 ครั้ง<br>(เช่น วันจันทร์) | 30–45 นาที | กำหนดเป้าหมายของสัปดาห์นี้, ประเมินความยากง่ายของงาน (Estimation) และสับหลีกการกระจายงาน (เช่น "ระบบดึงข้อมูลจาก Fitbit API") |
| **Asynchronous Stand-up**<br>(อัปเดตงานแบบพิมพ์ตอบ) | 3 ครั้งต่อสัปดาห์<br>(เช่น อังคาร/พฤหัสฯ/ศุกร์) | 5 นาที (สำหรับพิมพ์) | พิมพ์อัปเดตในช่องแชทส่วนกลาง:<br>1. *เมื่อวานทำอะไรเสร็จไปบ้าง?*<br>2. *วันนี้จะทำอะไรต่อ?*<br>3. *ติดปัญหา (Blocker) ตรงไหนไหม?* |
| **Weekly Sync & Demo**<br>(ตรวจงานและสรุปผล) | สัปดาห์ละ 1 ครั้ง<br>(เช่น วันศุกร์) | 30 นาที | เดโมโค้ดที่รันได้จริง (แม้จะยังอยู่แค่เครื่องตัวเอง), ทำ Retrospective สั้นๆ (Keep, Stop, Start) และร่วมยินดีกับความคืบหน้าของทีม |

## 2. กฎการสื่อสาร (Communication Rules)
เราต้องการสร้างสมดุลระหว่างการเรียน/การใช้ชีวิตส่วนตัว และการทำงานร่วมกันในทีม โดยเราจะใช้ **[ใส่ชื่อเครื่องมือ เช่น Discord / Line / Slack / MS Teams]** เป็นช่องทางหลักในการสื่อสาร

*   **คุยในช่องสาธารณะเป็นหลัก (Public First):** ให้พูดคุยเรื่องที่เกี่ยวกับเทคนิค การออกแบบ หรือการตัดสินใจในโปรเจกต์ผ่านช่องสาธารณะ (เช่น `#dev`, `#design`, `#general`) หลีกเลี่ยงการทักแชทส่วนตัว (DM) เพื่อให้สมาชิกรวมถึงเพื่อนร่วมทีมคนอื่นๆ รับทราบข้อมูลที่ตรงกันและช่วยเหลือกันได้ง่ายขึ้น
*   **ความเร็วในการตอบกลับ (Response Time):**
    *   **ในเวลาทำการ/เวลาเรียน (09:00 - 18:00 น.):** หากมีการแท็กชื่อบุคคล (`@ชื่อเพื่อน`) ขอความร่วมมือให้ตอบกลับภายใน **4 ชั่วโมง**
    *   **นอกเวลาทำการและวันหยุด:** ไม่มีการบังคับให้ตอบทันที เพื่อเคารพเวลาส่วนตัวของทุกคน
*   **ใช้ระบบตั้งกระทู้ (Threads):** เพื่อไม่ให้ข้อมูลปะปนกัน หากต้องการพูดคุยหัวข้อเฉพาะ เช่น เรื่องการออกแบบฐานข้อมูล ให้พูดคุยผ่านการตั้ง Thread ใต้โพสต์นั้นๆ ด้านช่องทางหลักจะได้ไม่รก
*   **กฎ 15 นาทีสำหรับปัญหาที่ติดขัด (The 15-Minute Rule):** หากคุณติดบั๊กหรือติดปัญหาทางเทคนิคเกิน 15 นาทีหลังจากพยายามหาทางแก้แล้ว ให้เขียนสรุปสิ่งทีได้ลองทำไปแล้วลงในช่อง `#dev` เพื่อขอความช่วยเหลือทันที อย่าปล่อยให้ตัวเองติดอยู่กับปัญหานานเกินไป!

## 3. ขั้นตอนการใช้งาน Git (Git Workflow)
เพื่อป้องกันไม่ให้เกิดปัญหาโค้ดพังหรือขัดแย้งกัน (Merge Conflicts) และเพื่อให้มั่นใจว่า Dashboard ของเราใช้งานได้ตลอดเวลา เราจะใช้ระบบ **Feature Branch Workflow** ดังนี้:

### รูปแบบการตั้งชื่อ Branch (Branch Naming)
ทุกครั้งที่เริ่มทำ Task ใหม่ ให้แตก Branch ออกมาจาก `main` (หรือ `develop`) โดยตั้งชื่อตามรูปแบบนี้:
*   `feature/ชื่อฟีเจอร์` (เช่น `feature/sleep-data-chart`)
*   `bugfix/ชื่อบั๊ก` (เช่น `bugfix/api-auth-error`)
*   `docs/เรื่องที่เขียน` (เช่น `docs/update-readme`)

### การเขียน Commit Message
เราจะเขียน Commit Message เป็นภาษาอังกฤษ โดยใช้คำสั่งที่เป็นปัจจุบัน (Imperative Mood) เพื่อความเป็นระเบียบ:
*   *ที่ควรทำ:* `feat: add Google Fit OAuth integration`
*   *ที่ควรทำ:* `fix: resolve chart scaling issue on mobile`
*   *ที่ควรหลีกเลี่ยง:* `updated some things`, `fixed bug`, `แก้บั๊กแล้ว`, `ส่งงาน`

### ขั้นตอนการสร้าง Pull Request (PR) และ Code Review
1.  **เปิด Draft PR:** ทันทีที่เริ่มเขียนโค้ด ให้สร้าง Pull Request ในสถานะ "Draft" ไว้ก่อน เพื่อให้เพื่อนๆ เห็นความคืบหน้าของงาน
2.  **พร้อมสำหรับการตรวจสอบ (Ready for Review):** เมื่อเขียนโค้ดและทดสอบเสร็จเรียบร้อยแล้ว ให้เปลี่ยนสถานะจาก Draft เป็น Ready for Review
3.  **เงื่อนไขการตรวจสอบโค้ด (Review Guidelines):**
    *   ต้องมีสมาชิกในทีมอย่างน้อย **1 คน** ทำการตรวจสอบ (Review) และกดอนุมัติ (Approve) ก่อน จึงจะทำการ Merge โค้ดได้
    *   ผู้ตรวจสอบควรดูเรื่อง: ความสะอาดของโค้ด (Clean Code), ไม่มีการฝัง API Key ไว้ในโค้ดโดยตรง (Security), และการใช้งานที่ลื่นไหล (UX consistent)
4.  **การ Merge:** หลังจากได้รับอนุมัติแล้ว เจ้าของ PR จะเป็นผู้ทำการกด Merge โค้ดของตัวเองเข้าสู่ Git หลัก

## 4. การตัดสินใจในทีม (Decision Making)
ในการพัฒนาโปรเจกต์ Quantified Self Dashboard อาจมีความคิดเห็นที่แตกต่างกันในเชิงเทคนิคหรือการออกแบบ (เช่น จะใช้ React หรือ Vue, จะใช้ Database แบบ SQL หรือ NoSQL) เราจะใช้กระบวนการดังต่อไปนี้เพื่อหาข้อยุติ:

1.  **พูดคุยและเปรียบเทียบ (เป้าหมาย 10 นาที):** สมาชิกที่เสนอไอเดียแต่ละฝั่ง ให้เขียนสรุปข้อดี-ข้อเสีย (Pros & Cons) สั้นๆ โดยเน้นที่ความง่ายในการพัฒนา ประสิทธิภาพ และเวลาที่มีจำกัดของโปรเจกต์
2.  **หลักการยอมรับความเสี่ยงร่วมกัน (Consent-Based Decision):** เราจะตั้งคำถามว่า *"มีใครคิดว่าตัวเลือกนี้จะทำให้โปรเจกต์เสียหายร้ายแรงหรือไม่?"* หากไม่มีข้อโต้แย้งที่รุนแรง แม้จะไม่ใช่ตัวเลือกที่ทุกคนชอบที่สุด แต่หากยอมรับความเสี่ยงได้ เราจะเลือกวิธีนั้นเพื่อก้าวเดินต่อไป
3.  **การโหวตเสียงข้างมาก:** หากยังไม่ได้ข้อสรุป ทีมจะใช้วิธีการโหวตคะแนนเสียงข้างมาก
4.  **ผู้ตัดสินชี้ขาด (Tie-Breaker):** ในกรณีที่คะแนนโหวตเท่ากัน ขอตกลงให้ **[ระบุชื่อเพื่อนที่เป็น Tech Lead / PM / หรือสุ่มเลือก]** เป็นผู้ตัดสินใจขั้นเด็ดขาด เพื่อให้ทีมสามารถไปต่อได้ โดยยึดหลัก *“Disagree and Commit” (แม้จะเห็นต่าง แต่เมื่อตัดสินใจแล้วทุกคนจะร่วมมือกันทำอย่างเต็มที่)*
