# Project: [LifeBalance]
LifeBalance เป็นแดชบอร์ดสำหรับติดตามสุขภาพส่วนบุคคลที่ออกแบบมาเพื่อช่วยให้ผู้ใช้งานสามารถดูแลสุขภาพได้สะดวกยิ่งขึ้น โดยเฉพาะวัยทำงานที่มีเวลาจำกัดในการวางแผนและติดตามการรับประทานอาหาร

ระบบสามารถคำนวณปริมาณแคลอรี บันทึกข้อมูลด้านสุขภาพ เช่น น้ำหนัก ส่วนสูง และข้อมูลการรับประทานอาหาร พร้อมทั้งสรุปผลและแสดงข้อมูลทั้งหมดในหน้าแดชบอร์ดเดียว ทำให้ผู้ใช้สามารถติดตามความคืบหน้าของตนเองได้อย่างง่ายดาย

LifeBalance ช่วยลดความยุ่งยากจากการคำนวณด้วยตนเองหรือการใช้งานหลายแอปพลิเคชันร่วมกัน ผู้ใช้จึงสามารถประหยัดเวลา วางแผนการรับประทานอาหารได้อย่างเหมาะสม และสร้างสมดุลในการดูแลสุขภาพในชีวิตประจำวันได้อย่างมีประสิทธิภาพ

## 🚀 Getting Started

โปรเจกต์ปัจจุบันเป็นเว็บแอปแบบ Modular Monolith โดยใช้ React + TypeScript สำหรับหน้าเว็บ, Node.js + Express สำหรับ API และ PostgreSQL + Prisma สำหรับฐานข้อมูล

### Prerequisites

- Git
- Node.js 22.12+
- Docker Desktop หรือ Docker Engine พร้อม Docker Compose

### Running the Application

เครื่องที่เตรียม PostgreSQL แบบพกพาไว้แล้วเปิดด้วย `npm run db:local` และ `npm run dev` ได้ ดู [วิธีเปิดและทดสอบบนเครื่องนี้](docs/local-testing.md) โดยเก็บค่าจริงใน `.env` เดิม ไม่ต้องคัดลอกทับใหม่

1. **ติดตั้ง dependencies:**
    ```bash
    npm install
    ```

2. **สร้างไฟล์ environment จากตัวอย่าง:**
    ```bash
    Copy-Item .env.example .env
    ```
    จากนั้นแก้ `JWT_SECRET` ใน `.env` เป็นค่าสุ่มที่มีความยาวอย่างน้อย 32 ตัวอักษร

3. **เปิด PostgreSQL และเตรียม schema:**
    ```bash
    docker compose up -d db
    npm run db:migrate
    ```

4. **เปิดระบบสำหรับพัฒนา:**
    ```bash
    npm run dev
    ```

หน้าเว็บอยู่ที่ `http://localhost:5173` และ API อยู่ที่ `http://localhost:3000`

### Verification

```bash
npm test
npm run build
```

### เว็บแอปมือถือและ AI วิเคราะห์รูป

ทุกขนาดจอใช้หน้าแอปเดียวกัน: วันนี้ / บันทึก / ความคืบหน้า / บัญชี หน้าอาหารรองรับถ่ายรูปหรือเลือกรูป → วิเคราะห์ → ตรวจแก้ → ยืนยันบันทึก ค่าสารอาหารจาก AI เป็นค่าประมาณ ไม่ใช่ผลวัดจริง

ใส่ค่าจริงใน `.env` เท่านั้น (`.env.example` เป็นตัวอย่างสาธารณะ):

```dotenv
AI_BASE_URL=https://gen.ai.kku.ac.th/upacth/api/v1
AI_API_KEY=
AI_MODEL=
AI_DAILY_SCAN_LIMIT=50
NUTRITION_API_KEY=
```

`AI_MODEL` ใช้ชื่อโมเดลที่มหาวิทยาลัยเปิดให้และรองรับภาพ ส่วน `NUTRITION_API_KEY` เป็น key ของ USDA/data.gov อีกบริการหนึ่ง ใช้เฉพาะการค้นข้อมูลสารอาหาร หากเว้นว่างยังใช้ AI ได้ อ่านรายละเอียดที่ [คู่มือตั้งค่า AI](docs/ai-setup.md)

หลังแก้ `.env` ให้บันทึกไฟล์และเริ่ม API ใหม่ ต้องเปิด PostgreSQL และรัน migration ก่อนใช้งานระบบจริง หน้าเว็บทดสอบกับ API จำลองไม่ยืนยันการบันทึกฐานข้อมูลจริง

ทดสอบ UI ด้วย Edge ที่ติดตั้งในเครื่อง:

```bash
npm run test:e2e
```

ชุดทดสอบ UI เปิดเว็บชั่วคราวที่ port 5174 และจำลองคำตอบ API จึงไม่ใช้ key หรือโควตา AI ดูขอบเขตผลทดสอบใน [รายงานทดสอบ](docs/test-report-mobile.md)

ขณะนี้ระบบรองรับการสมัครสมาชิก, เข้าสู่ระบบ, ออกจากระบบ, แก้ไขข้อมูลสุขภาพส่วนตัว, บันทึกอาหารพร้อมส่วนประกอบและรูปประกอบ, และบันทึกการออกกำลังกาย ระบบคำนวณ BMI, แคลอรีจากสารอาหาร, แคลอรีที่เผาผลาญ และ Net Calories รายวันให้อัตโนมัติ

# ข้อตกลงการทำงานร่วมกันในทีม (Ways of Working - WoW)

เอกสารฉบับนี้จัดทำขึ้นเพื่อกำหนดแนวทางปฏิบัติ กระบวนการทำงาน และมาตรฐานทางวิศวกรรมซอฟต์แวร์ของทีมเรา สำหรับโปรเจกต์ **The Quantified Self Dashboard** เพื่อให้ทุกคนทำงานร่วมกันได้อย่างราบรื่นและมีประสิทธิภาพ

---

## 1. รอบการประชุม (Meeting Cadence)
เพื่อให้การทำงานมีทิศทางที่ชัดเจนและอัปเดตงานได้รวดเร็ว เราจะแบ่งรอบการประชุมออกเป็น 3 ส่วนหลักดังนี้ครับ:

### 📅 การวางแผนประจำสัปดาห์ (Sprint Planning)
*   **ความถี่:** สัปดาห์ละ 1 ครั้ง (ทุกวันจันทร์)
*   **ระยะเวลา:** 30–45 นาที
*   **เป้าหมาย:** ร่วมกันกำหนดเป้าหมายของสัปดาห์นั้น ประเมินความยากง่ายของงาน และแบ่งงานกันอย่างชัดเจน (เช่น ใครจะทำหน้า UI กราฟ หรือใครจะทำระบบเชื่อมต่อ API การนอนหลับ)

### 💬 การอัปเดตงานด่วน (Asynchronous Stand-up)
*   **ความถี่:** 3 ครั้งต่อสัปดาห์ (วันอังคาร, พฤหัสบดี, และศุกร์)
*   **ระยะเวลา:** ใช้เวลาพิมพ์อัปเดตสั้นๆ ไม่เกิน 5 นาที
*   **เป้าหมาย:** พิมพ์สรุปความคืบหน้าในช่องแชทส่วนกลาง โดยตอบ 3 คำถามหลัก:
    1. เมื่อวานทำอะไรเสร็จไปบ้าง?
    2. วันนี้จะทำอะไรต่อ?
    3. มีปัญหาตรงไหนที่ต้องการให้ช่วยไหม?

### 🏆 การตรวจงานและสรุปผล (Weekly Sync & Demo)
*   **ความถี่:** สัปดาห์ละ 1 ครั้ง (ทุกวันศุกร์)
*   **ระยะเวลา:** 30 นาที
*   **เป้าหมาย:** นำโค้ดที่รันได้จริงมาเดโมแสดงให้เพื่อนดู ร่วมกันสะท้อนผลการทำงาน (Retrospective) ว่าอะไรที่ดีอยู่แล้ว หรือมีอะไรที่ต้องปรับปรุง พร้อมทั้งสรุปจบสัปดาห์ร่วมกัน

*หมายเหตุ: ทุกการประชุมจะเริ่มตรงเวลา หากใครติดเรียนหรือติดธุระด่วน ให้แจ้งในกลุ่มล่วงหน้าอย่างน้อย 2 ชั่วโมง*

## 2. กฎการสื่อสาร (Communication Rules)
เราใช้ **[ใส่ชื่อเครื่องมือ เช่น Discord / Line / Slack / MS Teams]** เป็นช่องทางหลัก โดยแบ่งสัดส่วนการสื่อสารดังนี้:

*   **คุยงานในที่แจ้งเป็นหลัก (Public First):** หลีกเลี่ยงการทักแชทส่วนตัว (DM) เพื่อคุยเรื่องโค้ดหรือการออกแบบ ให้พิมพ์คุยในช่องสาธารณะ (เช่น `#dev`,  `#design`) เพื่อให้ทุกคนในทีมได้รับข้อมูลที่ตรงกัน และช่วยกันแก้ปัญหาได้เร็วขึ้น
*   **เวลาในการตอบกลับ (Response Time):**
    *   **ในเวลาเรียน/เวลาทำการ (09:00 - 18:00 น.):** หากโดนแท็กชื่อโดยตรง (`@ชื่อเรา`) ขอความร่วมมือให้ตอบกลับภายใน **4 ชั่วโมง**
    *   **นอกเวลาเรียนและวันหยุด:** ไม่บังคับตอบทันที สามารถตอบเมื่อสะดวกเพื่อเคารพเวลาส่วนตัวของทุกคน
*   **คุยเป็นประเด็นย่อย (Use Threads):** หากคุยเรื่องใดเรื่องหนึ่งยาวๆ เช่น "วิธีแก้บั๊กหน้าแสดงผลสถิติเดิน" ให้กดคุยต่อใน Thread ใต้โพสต์นั้นๆ เพื่อไม่ให้ข้อความหลักของกลุ่มรก
*   **กฎ 15 นาทีห้ามจมกับปัญหา:** หากเขียนโค้ดแล้วติดบั๊กเกิน 15 นาทีหลังจากพยายามหาทางแก้แล้ว ให้หยุดทำ แล้วเขียนสรุปสิ่งที่เจอพร้อมรูปประกอบลงช่องแชทเพื่อขอความช่วยเหลือทันที

## 3. ขั้นตอนการใช้งาน Git (Git Workflow)
เพื่อป้องกันไม่ให้เกิดปัญหาโค้ดพังหรือเขียนทับกัน เราจะแบ่งขั้นตอนการทำโค้ดออกเป็นสัดส่วนชัดเจน:

### 1) การตั้งชื่อ Branch (Branch Naming)
เมื่อจะเริ่มทำอะไรใหม่ ให้แตก Branch ออกมาจาก `main` (หรือ `develop`) และใช้ชื่อนำหน้าดังนี้:
*   `feature/ชื่อฟีเจอร์` (สำหรับเพิ่มฟีเจอร์ใหม่ เช่น `feature/sleep-data-chart`)
*   `bugfix/ชื่อบั๊ก` (สำหรับแก้บั๊ก เช่น `bugfix/api-auth-error`)
*   `docs/เรื่องที่เขียน` (สำหรับงานเอกสาร เช่น `docs/update-readme`)

### 2) การเขียน Commit Message
ใช้ภาษาอังกฤษที่สั้น กระชับ และสื่อความหมายชัดเจน:
*   *ตัวอย่างที่ดี:* `feat: add Google Fit OAuth integration`
*   *ตัวอย่างที่ดี:* `fix: resolve chart scaling issue on mobile`
*   *หลีกเลี่ยงคำคลุมเครือ:* `updated`, `fixed bug`, `แก้แล้ว`, `งานน้า`

### 3) ขั้นตอน Pull Request (PR) & Code Review
*   **เปิด Draft PR:** เมื่อเริ่มเขียนโค้ด ให้สร้าง PR ในสเตตัส "Draft" ไว้ทันทีเพื่อโปร่งใสว่าเรากำลังทำอะไรอยู่
*   **ขอตรวจโค้ด (Ready for Review):** เมื่อเขียนเสร็จและทดสอบแล้ว ให้เปลี่ยนสเตตัสพร้อมแท็กเพื่อนมาตรวจ
*   **คนตรวจคุยกัน:** ต้องมีเพื่อนในทีมอย่างน้อย **1 คน** เข้ามาอ่านโค้ด กด Approve และให้ความเห็นก่อนเสมอ ถึงจะทำการรวมโค้ด (Merge) ได้
*   **การ Merge:** เจ้าของโค้ด (คนเปิด PR) จะเป็นผู้กดปุ่ม Merge ด้วยตัวเองหลังจากเพื่อนอนุมัติแล้ว

## 4. การตัดสินใจในทีม (Decision Making)
หากมีความเห็นต่างกันในเรื่องของการออกแบบหน้าจอ หรือการเขียนโค้ด (เช่น เลือกใช้ library ตัวไหนดี) เราจะใช้ขั้นตอนการแก้ปัญหาเป็นลำดับสัดส่วนดังนี้:

*   **ขั้นตอนที่ 1 (แชร์เหตุผล):** ให้ผู้เสนอทางเลือกแต่ละฝ่าย เขียนอธิบาย "ข้อดี-ข้อเสีย" สั้นๆ โดยจำกัดเวลาพูดคุยกันไม่เกิน 10 นาที โดยพิจารณาจากเรื่อง เวลาที่ใช้ทำ ความยาก และสโคปของโปรเจกต์
*   **ขั้นตอนที่ 2 (รับฟังอุปสรรค):** ถามคนในทีมว่า *"หากเลือกทางนี้ จะมีใครทำงานต่อไม่ได้ หรือส่งผลร้ายแรงต่อโปรเจกต์ไหม?"* หากไม่มีข้อขัดแย้งที่ยอมรับไม่ได้ จะเลือกทางนั้นทันที แม้จะไม่ใช่ทางที่ทุกคนชอบที่สุด
*   **ขั้นตอนที่ 3 (โหวตเสียงข้างมาก):** หากยังหาทางออกไม่ได้ ให้คนในทีมทุกคนทำการโหวต
*   **ขั้นตอนที่ 4 (ชี้ขาด):** หากคะแนนเสียงเท่ากัน ขอตกลงให้ **[ใส่ชื่อทีมงานที่เป็นผู้ชี้ขาด/เช่น Tech Lead หรือสุ่มเลือก]** เป็นผู้ตัดสินใจขั้นสุดท้าย เพื่อให้ทีมเดินหน้าต่อได้ทันเวลา
